Classes & Objects: The Building Blocks

Understand the foundation of object-oriented programming

🏗️ What are Classes and Objects?

A class is a blueprint for creating objects. Think of it as a template that defines what data (attributes) and behaviors (methods) objects will have.

An object is an instance of a class—a concrete realization of that blueprint with specific values.

💡 Analogy: A Blueprint vs. A House

A class is like an architectural blueprint. The blueprint specifies that a house has walls, doors, and windows—but it's not a real house. An object is like an actual house built from that blueprint. You can build many houses from one blueprint, and each house has specific characteristics (color, size, number of rooms).

✨ Real-World Example

Class: Car (blueprint: has engine, wheels, doors)

Objects:

  • Your Tesla (red, electric, 4 doors)
  • Your friend's Honda (silver, gasoline, 2 doors)
  • Taxi cab (yellow, hybrid, 4 doors)

💻 Class Syntax and Structure

Here's the basic structure of a C++ class:

C++ class ClassName { private: // Private data members (attributes) int attributeOne; string attributeTwo; public: // Public methods (behaviors) void methodOne(); int getAttributeOne(); void setAttributeOne(int value); };

Key Components:

  • private: Data that only the class can access
  • public: Methods and data that anyone can access
  • Attributes: Variables that hold the object's state
  • Methods: Functions that define the object's behavior

📝 Complete Example: A Bank Account Class

C++ class BankAccount { private: string accountHolder; double balance; public: // Constructor BankAccount(string name, double initialBalance) { accountHolder = name; balance = initialBalance; } // Getter method double getBalance() { return balance; } // Setter/Action method void deposit(double amount) { if (amount > 0) { balance += amount; } } void withdraw(double amount) { if (amount > 0 && amount <= balance) { balance -= amount; } } }; // Using the class int main() { BankAccount account("Alice", 1000); account.deposit(500); cout << account.getBalance(); // Output: 1500 return 0; }

🔧 Constructors and Destructors

Constructors are special methods that initialize an object when it's created.

Destructors clean up resources when an object is destroyed.

Feature Constructor Destructor Purpose Initialize object Clean up resources Called When object is created When object is destroyed Syntax ClassName() { ... } ~ClassName() { ... } Parameters Can have parameters No parameters Multiple? Yes (overloading) Only one
C++ class Student { private: string name; int age; public: // Constructor Student(string n, int a) { name = n; age = a; cout << "Student created: " << name << endl; } // Destructor ~Student() { cout << "Student destroyed: " << name << endl; } };

🔐 Access Modifiers: public, private, protected

Access modifiers control who can access class members:

❌ Common Misconception

Wrong: "I should make everything public for convenience."

Right: Hide implementation details (private), expose only necessary interfaces (public). This protects your code from misuse.

🎯 Key Takeaways - Module 1

  2. Classes bundle data (attributes) and functions (methods) together
  3. Constructors initialize objects; destructors clean them up
  4. Access modifiers (public, private, protected) control visibility
  5. Encapsulation hides internal details and protects data integrity

Inheritance & Polymorphism: Code Reuse and Flexibility

Learn how to build class hierarchies and create flexible code

🔗 Inheritance: Building on Existing Code

Inheritance allows a class to inherit attributes and methods from another class. The class being inherited from is called the base class or parent class, and the class doing the inheriting is called the derived class or child class.

💡 Analogy: Biological Inheritance

You inherit traits from your parents (base class). You have all the characteristics of humans, but you're a specific individual (derived class). A Dog inherits from Animal—it has all the properties of an animal (can eat, sleep, move) but adds dog-specific behaviors (bark, wag tail).

✨ Vehicle Hierarchy

  • Base Class: Vehicle (has speed, fuel, wheels)
  • Derived Classes:
    • Car (inherits from Vehicle, adds doors, trunk)
    • Motorcycle (inherits from Vehicle, adds handlebar type)
    • Truck (inherits from Vehicle, adds cargo capacity)
C++ // Base Class class Vehicle { protected: string model; double speed; public: Vehicle(string m, double s) { model = m; speed = s; } void accelerate() { speed += 10; } }; // Derived Class class Car : public Vehicle { private: int doors; public: Car(string m, double s, int d) : Vehicle(m, s) { doors = d; } void openTrunk() { cout << "Trunk opened" << endl; } }; // Usage int main() { Car myCar("Tesla", 100, 4); myCar.accelerate(); // Inherited from Vehicle myCar.openTrunk(); // Car-specific return 0; }

📊 Types of Inheritance

Type Syntax Use Case Example Single class Derived : public Base One parent Car inherits from Vehicle Multiple class D : public B1, public B2 Multiple parents AmphibiousCar from Car and Boat Multilevel A → B → C Inheritance chain Vehicle → Car → SportsCar Hierarchical Multiple children from one parent Common base Vehicle → Car, Truck, Motorcycle

❌ Common Misconception

Wrong: "Multiple inheritance is always the best because it's more powerful."

Right: Multiple inheritance creates complexity and the "diamond problem." Use composition or interfaces when possible.

🎭 Polymorphism: One Interface, Many Forms

Polymorphism means "many forms." It allows objects of different classes to be treated through the same interface.

💡 Analogy: Remote Control

A TV remote has a "power" button. Whether you're controlling a Samsung TV, an LG TV, or a Sony TV, the button does the same thing—but the implementation is different. Same interface, different behaviors.

C++ // Base Class class Animal { public: virtual void speak() { cout << "Some generic sound" << endl; } }; // Derived Classes class Dog : public Animal { public: void speak() override { cout << "Woof! Woof!" << endl; } }; class Cat : public Animal { public: void speak() override { cout << "Meow!" << endl; } }; int main() { Animal* animal1 = new Dog(); Animal* animal2 = new Cat(); animal1->speak(); // Outputs: Woof! Woof! animal2->speak(); // Outputs: Meow! return 0; }

Key Concept: Virtual Functions

The virtual keyword tells the compiler that this method might be overridden by derived classes. The override keyword (C++11+) indicates that a method is overriding a base class method.

⚡ Compile-time vs Runtime Polymorphism

Feature Compile-time (Overloading) Runtime (Overriding) When resolved During compilation During program execution Method Function overloading Virtual functions Inheritance required No Yes Performance Faster (known at compile) Slightly slower (runtime) Example print(int), print(string) Animal* -> Dog/Cat speak()
C++ // Compile-time Polymorphism: Overloading class Printer { public: void print(int x) { cout << "Int: " << x << endl; } void print(double x) { cout << "Double: " << x << endl; } void print(string x) { cout << "String: " << x << endl; } }; int main() { Printer p; p.print(42); // Calls print(int) p.print(3.14); // Calls print(double) p.print("Hello"); // Calls print(string) return 0; }

🎯 Key Takeaways - Module 2

  1. Inheritance enables code reuse through class hierarchies
  2. A derived class inherits public and protected members from its base class
  3. Virtual functions enable runtime polymorphism
  4. Overloading (compile-time) and overriding (runtime) are different concepts
  5. Polymorphism allows unified interfaces for different object types

Encapsulation & Abstraction: Data Protection and Interface Design

Master the art of hiding complexity and protecting data

🔒 Encapsulation: Data Hiding

Encapsulation is the bundling of data (attributes) and methods (functions) into a single unit (class) while hiding the internal details from the outside world.

💡 Analogy: A Car's Engine

You interact with your car through a steering wheel, pedals, and gear shift. You don't need to know exactly how the engine works internally. The complex engine mechanics are hidden from you. If the manufacturer improves the engine, your interaction method stays the same. This is encapsulation.

✨ BankAccount Example

Users shouldn't directly modify the balance. Instead, they use public methods like deposit() and withdraw() which perform validation.

C++ // BAD: Direct access to data class BadBankAccount { public: double balance; // Anyone can change this! }; // Usage - DANGEROUS int main() { BadBankAccount acc; acc.balance = 1000; acc.balance = -5000; // Invalid! No validation! return 0; } // GOOD: Encapsulation with validation class GoodBankAccount { private: double balance; public: GoodBankAccount(double initial) { if (initial >= 0) balance = initial; else balance = 0; } bool withdraw(double amount) { if (amount > 0 && amount <= balance) { balance -= amount; return true; } return false; } bool deposit(double amount) { if (amount > 0) { balance += amount; return true; } return false; } double getBalance() const { return balance; } }; // Usage - SAFE int main() { GoodBankAccount acc(1000); acc.withdraw(500); acc.withdraw(6000); // Fails safely - returns false return 0; }

❌ Common Misconception

Wrong: "Encapsulation means using private members. That's all."

Right: Encapsulation is about controlling access through well-designed public interfaces (getters/setters, methods) that validate and protect data.

🎛️ Getters and Setters

Getters (accessor methods) retrieve data. Setters (mutator methods) modify data with validation.

C++ class Person { private: string name; int age; public: // Getter for name string getName() const { return name; } // Setter for name void setName(string n) { if (!n.empty()) { name = n; } } // Getter for age int getAge() const { return age; } // Setter for age with validation void setAge(int a) { if (a > 0 && a < 150) { age = a; } } };

Benefits of Getters/Setters:

  • Validate data before storing
  • Add read-only properties (getter only)
  • Implement computed properties
  • Add logging/debugging
  • Change implementation without affecting API

🎭 Abstraction: Simplifying Complexity

Abstraction is the process of hiding complex internal details and showing only the essential features of an object.

💡 Analogy: Using a Coffee Machine

You press a button and get coffee. You don't need to understand the heating elements, pressure valves, and water pumps inside. The machine abstracts away the complexity. All you see is the simple interface: buttons and a cup holder.

Abstract Classes: Classes that cannot be instantiated but define an interface for derived classes.

C++ // Abstract Base Class class Shape { public: // Pure virtual function (must be overridden) virtual double getArea() = 0; virtual double getPerimeter() = 0; // Virtual destructor virtual ~Shape() {} }; // Cannot do: Shape s; ERROR - Shape is abstract class Circle : public Shape { private: double radius; public: Circle(double r) : radius(r) {} // Must implement pure virtual functions double getArea() override { return 3.14159 * radius * radius; } double getPerimeter() override { return 2 * 3.14159 * radius; } }; int main() { // Circle c; // OK // Shape s; // ERROR - abstract Shape* shape = new Circle(5); // OK - pointer to abstract cout << shape->getArea(); return 0; }

❌ Common Misconception

Wrong: "Abstraction and encapsulation are the same thing."

Right: Encapsulation hides implementation details; abstraction shows only what's relevant. Related but different concepts.

⚙️ Interfaces: Pure Virtual Functions

A pure virtual function has no implementation in the base class. Derived classes must provide their own implementation.

C++ // Interface-like abstract class class DatabaseInterface { public: virtual bool connect(string connectionString) = 0; virtual bool disconnect() = 0; virtual bool query(string sql) = 0; virtual ~DatabaseInterface() {} }; // MySQL implementation class MySQLDatabase : public DatabaseInterface { public: bool connect(string connectionString) override { // MySQL-specific connection logic cout << "Connected to MySQL" << endl; return true; } bool disconnect() override { cout << "Disconnected from MySQL" << endl; return true; } bool query(string sql) override { cout << "Executing on MySQL: " << sql << endl; return true; } }; // PostgreSQL implementation class PostgreSQLDatabase : public DatabaseInterface { public: bool connect(string connectionString) override { // PostgreSQL-specific connection logic cout << "Connected to PostgreSQL" << endl; return true; } bool disconnect() override { cout << "Disconnected from PostgreSQL" << endl; return true; } bool query(string sql) override { cout << "Executing on PostgreSQL: " << sql << endl; return true; } }; int main() { DatabaseInterface* db = new MySQLDatabase(); db->connect("localhost"); db->query("SELECT * FROM users"); db->disconnect(); // Switch to PostgreSQL easily! // db = new PostgreSQLDatabase(); return 0; }

🎯 Key Takeaways - Module 3

  1. Encapsulation protects data integrity through controlled access
  2. Getters and setters provide validation points for data modification
  3. Abstraction hides complexity behind simple interfaces
  4. Abstract classes define contracts for derived classes
  5. Pure virtual functions enforce implementation in derived classes

Master professional OOP design patterns and architecture

🏗️ SOLID Principles: Design Guidelines

SOLID is an acronym for five design principles that make software more maintainable, flexible, and scalable.

S - Single Responsibility Principle

A class should have only one reason to change. It should do one thing and do it well.

C++ // BAD: User class does too much class User { void saveToDatabase() { } // Database responsibility void sendEmail() { } // Email responsibility void validatePassword() { } // Validation responsibility }; // GOOD: Each class has one responsibility class User { void validatePassword() { } }; class UserRepository { void saveToDatabase(User u) { } }; class EmailService { void sendEmail(string to, string message) { } };

O - Open/Closed Principle

Classes should be open for extension but closed for modification.

C++ // BAD: Violates O/C - must modify when adding new shapes class Area { double calculateArea(Shape* s) { if (s->type == "Circle") { return 3.14 * radius * radius; } else if (s->type == "Square") { return side * side; } } }; // GOOD: Extend without modifying class Shape { virtual double area() = 0; }; class Circle : public Shape { double area() override { return 3.14 * r * r; } }; class Square : public Shape { double area() override { return side * side; } };

L - Liskov Substitution Principle

Objects of a derived class should be usable wherever the base class is expected.

C++ // BAD: Bird can fly, but Penguin can't class Bird { virtual void fly() { } }; class Penguin : public Bird { void fly() override { throw "Penguins can't fly!"; } }; // GOOD: Use composition and proper hierarchy class Bird { }; class FlyingBird : public Bird { virtual void fly() { } }; class Penguin : public Bird { // Not a flying bird void swim() { } };

I - Interface Segregation Principle

Clients should not depend on interfaces they don't use.

C++ // BAD: Force to implement unused methods class Worker { virtual void work() = 0; virtual void eat() = 0; }; class Robot : public Worker { void work() override { } void eat() override { } // Robots don't eat! }; // GOOD: Segregate interfaces class Workable { virtual void work() = 0; }; class Eatable { virtual void eat() = 0; }; class Robot : public Workable { void work() override { } // No eat() method needed };

D - Dependency Inversion Principle

Depend on abstractions, not concretions.

C++ // BAD: High-level depends on low-level class MySQLDatabase { bool query(string sql) { } }; class UserService { private: MySQLDatabase db; // Tightly coupled to MySQL }; // GOOD: Both depend on abstraction class DatabaseInterface { virtual bool query(string sql) = 0; }; class MySQLDatabase : public DatabaseInterface { bool query(string sql) override { } }; class UserService { private: DatabaseInterface* db; // Depends on abstraction };

🎨 Common Design Patterns

Design patterns are proven solutions to common programming problems.

1. Singleton Pattern

Ensures only one instance of a class exists.

C++ class Logger { private: static Logger* instance; Logger() { } // Private constructor public: static Logger* getInstance() { if (instance == nullptr) { instance = new Logger(); } return instance; } void log(string message) { cout << message << endl; } }; Logger* Logger::instance = nullptr; // Usage int main() { Logger* log1 = Logger::getInstance(); Logger* log2 = Logger::getInstance(); // log1 and log2 point to the same object return 0; }

2. Factory Pattern

Creates objects without specifying exact classes.

C++ class Vehicle { public: virtual void drive() = 0; }; class Car : public Vehicle { public: void drive() override { cout << "Driving car" << endl; } }; class Truck : public Vehicle { public: void drive() override { cout << "Driving truck" << endl; } }; class VehicleFactory { public: static Vehicle* createVehicle(string type) { if (type == "car") return new Car(); if (type == "truck") return new Truck(); return nullptr; } }; // Usage int main() { Vehicle* v1 = VehicleFactory::createVehicle("car"); Vehicle* v2 = VehicleFactory::createVehicle("truck"); v1->drive(); // Driving car v2->drive(); // Driving truck return 0; }

3. Observer Pattern

Notifies multiple observers when state changes.

C++ class Subject; class Observer { public: virtual void update(Subject* s) = 0; }; class Subject { private: vector observers; public: void attach(Observer* obs) { observers.push_back(obs); } void setState(int state) { // Notify all observers for (auto obs : observers) { obs->update(this); } } }; class ConcreteObserver : public Observer { public: void update(Subject* s) override { cout << "Observer notified!" << endl; } };

✨ OOP Best Practices

✓ Do's

  • Use meaningful class and method names
  • Keep classes focused and small
  • Prefer composition over inheritance
  • Use const references to avoid copies
  • Document complex logic with comments
  • Write tests for your classes
  • Use virtual destructors in base classes
  • Follow the DRY principle (Don't Repeat Yourself)

❌ Don'ts

  • Don't overuse inheritance (prefer composition)
  • Don't make everything public
  • Don't create classes for everything
  • Don't forget to handle exceptions
  • Don't use global variables
  • Don't violate SOLID principles
  • Don't create deeply nested hierarchies
  • Don't ignore memory management

📚 Complete Summary

Core Concepts

1. Classes and Objects

Classes are blueprints that define structure and behavior. Objects are instances created from those blueprints. Every class should have constructors to initialize objects and destructors to clean up resources.

2. Encapsulation

Bundle data and methods together while hiding implementation details. Use access modifiers (private, public, protected) to control visibility. Implement getters and setters for validated data access.

3. Inheritance

Enable code reuse by creating hierarchies where derived classes inherit from base classes. Use protected access to share implementation details with derived classes. Remember: inheritance represents "is-a" relationships.

4. Polymorphism

Use virtual functions to enable runtime polymorphism. Derived classes override base class methods. Always use virtual destructors in base classes. Use base class pointers/references to work with derived objects.

5. Abstraction

Hide complexity behind simple interfaces. Use abstract classes with pure virtual functions. Define contracts that derived classes must fulfill. Abstractions enable loose coupling and high flexibility.

6. Design Patterns

Apply proven solutions like Singleton (one instance), Factory (object creation), Observer (state changes). Patterns solve recurring design problems and make code more maintainable.

7. SOLID Principles

Guide your design with Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion. These principles create flexible, maintainable, and scalable code.
